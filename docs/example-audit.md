# Example audit (October 2026)

The four projects in `examples/` were generated by the original pipeline
(Architect → Interface → Implementation → Testing → Review, files returned as
JSON) with `grok-4-1-fast-non-reasoning`. Every one was recorded as a successful
build. This audit installed each project's dependencies and ran its generated
tests to see whether that was true.

## Results

| Example | Generated tests passing | Other problems |
|---|---|---|
| rest-api (TypeScript) | 69 / 92 (14 of 27 test files fail) | 48 `tsc` errors; 32 files on disk that no spec owns |
| fullstack-todo (TypeScript) | 53 / 87 (12 of 16 test files fail) | |
| cli-tool (Python) | 54 / 81, plus 1 file that does not parse | configured `test_command` points at `src/tests/`, which does not exist |
| data-pipeline (Python) | 34 / 65, plus 9 files that fail to import | `schemas.py` and a `schemas/` package collide; `test_command` errors |

(Two cli-tool failures are `PermissionError` tests that cannot pass when run as
root; they are not counted as generator faults.)

None of these projects works, yet every build was recorded as a success.

## Root causes

1. **Code inside JSON gets corrupted.** Agents returned files as JSON string
   values. A model writing `'[\n  {'` inside Python inside JSON produced a real
   line break when decoded, and `test_convert.py` no longer parses.
2. **Nodes did not know about each other's files.** Each node planned its files
   in isolation. Two nodes wrote the same test file (the later one silently
   replaced the other's), produced near-duplicate modules (`userService.ts`,
   `user-store.ts`, `user.repository.ts`, two `auth.controller.ts`), and chose
   colliding module names (`schemas.py` vs `schemas/`).
3. **Agents did not know how the project runs.** Nothing told them where tests
   go, how they are run, or how imports resolve, so they guessed: relative
   imports that fail under pytest, tests in directories the test command never
   reads.
4. **Nothing deterministic checked the output.** Missing imports (`json`,
   `Dict`), syntax errors and unresolved modules are cheap to detect by running
   code, but the only gate was an LLM review, which passed all of them. The test
   gate was effectively off: the configured commands either found no tests or
   had `|| true` appended.
5. **Tests guessed at details the spec left open.** Many failures are disputes
   about exact error messages or JSON spacing that the spec never pinned down;
   code and tests were each internally plausible and mutually inconsistent.
6. **Failures were never fed back.** A failing test run rolled back the whole
   cascade and discarded the output, so no attempt was ever made to fix the
   specific error.

## What changed in response

- Agents return files as `<file path="...">` blocks with verbatim contents. No
  code passes through JSON.
- Every prompt includes the project's file map with owners. Writing a file owned
  by another spec, or any existing file specdiff did not generate, is rejected.
- Every prompt states the language, the output directory as the import root,
  and the exact test command.
- After each node is generated, deterministic checks run in order: path and
  ownership checks, Python syntax, an optional `check_command` (for example
  `npx tsc --noEmit`), then `test_command`. The LLM review runs only once those
  pass.
- Any failure goes to a repair stage with the actual error output, up to
  `max_retries` times.
- The plan stage pins down exact names, signatures and error messages before
  code and tests are written in parallel, so both are held to the same contract.
- Each node is saved as soon as it passes. A failing node is rolled back on its
  own and only the specs downstream of it are skipped.

What these changes cannot fix is item 5 when the spec itself is vague. That is
the job of human-owned acceptance tests and of `specdiff review`, which flags
specs that leave error messages and formats unstated.

The example snapshots are left as they were, as a record of the old pipeline's
output. Regenerating them with the new pipeline needs an API key.
